# Enterprise ambient mode

Use the selected release's [ambient Helm guide](https://docs.solo.io/istio/latest/setup/install/manual/) and [requirements](https://docs.solo.io/istio/latest/setup/requirements/). Establish Kubernetes platform, Gateway API CRDs, existing chart owners and values, Istio revision, CNI, ztunnel, trust roots, and namespace enrollment before rendering or applying changes. Install or upgrade base, istiod, CNI, and ztunnel in the order documented for that release. Check release notes before replacing an operator-owned installation with Helm.

On a populated cluster, inspect `helm get manifest` for the existing `istio-base` release before uninstalling it: Helm-managed CRDs can be removed with the release and delete their custom resources. Preserve those resources and use an in-place base upgrade when the selected release supports it. Compare the old and new CRD sets. Check the installed Gateway API bundle and other controllers that use it before applying a bundle; do not downgrade shared CRDs. If the trust domain changes, find AuthorizationPolicy principals and other identity references that still name the old domain and plan their migration explicitly.

Preserve service account identity and current policies while enrolling workloads. Inspect sidecar injection and ambient labels to prevent ambiguous capture. Use [ztunnel authorization](https://docs.solo.io/istio/latest/security/authorization/ztunnel-authz/) for supported L4 controls and [waypoint authorization](https://docs.solo.io/istio/latest/security/authorization/waypoint-authz/) for supported L7 controls. Verify waypoint attachment for the actual service and source path. Check NetworkPolicy and health checks before enforcing restrictive policy.

For multicluster, use the selected release's [ambient multicluster architecture](https://docs.solo.io/istio/latest/about/multicluster/) and [installation guide](https://docs.solo.io/istio/latest/multicluster/install/default/manual/). Confirm the Solo distribution and Enterprise-level entitlement that this peering feature requires. Inventory each context, cluster name, network, trust root, east-west/peering gateway, and service discovery scope. The Solo control planes exchange service information over mTLS-secured xDS through `istio-remote` gateways; they do not need upstream community multicluster's remote kubeconfig secrets or remote Kubernetes API watches. Do not mix the two mechanisms or migrate between them without the selected release's migration guidance. Check `global.multiCluster.clusterName` and UI cluster labels against the intended names; a mismatch can make telemetry and discovered resources appear under different clusters. Do not copy a single-cluster command across contexts without its cluster-specific values. Test cross-cluster reachability and failover only within the customer's authorized traffic limits.

For a bidirectional routing check, publish a small global Service hosted only in each cluster and call each one from the opposite cluster. Verify the returned workload's cluster and the ztunnel access log's source, destination, and SPIFFE identities. Also verify both remote Gateway conditions and the release-matched `istioctl multicluster check` result.

If the request includes Solo UI, consult [UI setup](https://docs.solo.io/istio/latest/ui/setup/setup/), [OIDC setup](https://docs.solo.io/istio/latest/ui/security/), and [licensing](https://docs.solo.io/istio/latest/about/images/licensing/). The istiod license Secret and UI management Secret can require different data keys; check each chart's current instructions. Prefer Secret references or mounted files to inline license values. Configure external IdP and explicit RBAC mappings for shared or long-lived access; verify a reader and an administrator with their intended permissions.
